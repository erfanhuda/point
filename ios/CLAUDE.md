# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A simple point-of-sale app for iOS — CRUD for an item catalog (with dynamic variants), a sell-transaction form, and stock tracking (stock-in / stock-out / correction / opname) — built with SwiftUI and MVVM. Sibling project to `../../ledger`; follows the same toolchain and structural conventions.

This is the **iOS app only** — it lives at `point/ios/` so that `point/design/` (Figma wireframes and design references) can sit alongside it without mixing design assets into the Xcode project tree.

## Toolchain constraint (important)

Same as `../../ledger`: targets **iOS 16.0 / Swift 5.7**, built against **Xcode 14.2** (no SwiftData, no visual Core Data model editor on this machine).
- **The Core Data model is built entirely in code**, in `Persistence/CoreData/CoreDataModel.swift` — there is no `.xcdatamodeld` XML file to open in Xcode. See "Persistence" below before adding an entity/attribute.
- **The `.xcodeproj` is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen), not hand-maintained.** A prebuilt binary lives at `~/.local/bin/xcodegen`. **Never hand-edit `Point.xcodeproj` — edit `project.yml` and regenerate.**

## Architecture

Strict MVVM, under `Point/`:

- **Models/** — plain `Codable`/`Hashable` value types: `Item`, `ItemVariant`, `StockMovement`, `StockMovementType`, `Transaction`, `TransactionLine`. `Transaction.subtotal`/`discountedSubtotal`/`taxAmount`/`total` are computed properties, never stored.
- **Persistence/** — Core Data-backed (`ItemEntity`, `StockMovementEntity`, `TransactionEntity`). `ItemVariant` lists and `TransactionLine` lists are stored as **JSON-encoded `Data` blobs** on their owning entity rather than as separate related entities — nothing ever queries a variant or a line independently of its parent, so a Core Data relationship would only add ceremony. `ItemRepository`/`StockMovementRepository`/`TransactionRepository` protocols are implemented by `CoreDataItemRepository`/`CoreDataStockMovementRepository`/`CoreDataTransactionRepository` against `CoreDataStack`; ViewModels depend on the protocols only. `PointTests` substitutes an in-memory `CoreDataStack(inMemory: true)` rather than mocking the protocols, since the JSON round-trip through Core Data is itself worth exercising (see `CoreDataPersistenceTests`).
- **Utilities/StockCalculator** — current stock and the per-item "stock card" (running balance) are **never stored**, always derived on demand by summing an item's `StockMovement`s in date order — the same "derive, don't store" approach `../../ledger` uses for account balances.
- **ViewModels/** — `@MainActor` `ObservableObject`s, one per screen/flow (`ItemListViewModel`, `ItemFormViewModel`, `ItemDetailViewModel`, `StockMovementFormViewModel`, `TransactionListViewModel`, `TransactionFormViewModel`).
- **Views/** — grouped by feature (`Items/`, `Sales/`, `Stock/`, `Shared/`).

### Item codes

`Item.code` (e.g. `"ITM-0001"`) is assigned once by `CoreDataItemRepository.create(_:)` from the current row count — never edited afterward, never reused after a delete. `ItemRepository.update(_:)` (used for edits) keeps the existing code.

### Item variants

An `ItemVariant` is a name + add-on price, an optional `linkedItemID` pointing at another `Item` profile, or both at once — `linkedItemID` just adds a relationship on top, it doesn't replace the name/add-on-price fields. Edited as a dynamic CRUD list inside `ItemFormView` via `ForEach($viewModel.variants)`.

### Sell transactions and stock

Saving a `Transaction` (`TransactionFormViewModel.save()`) does two things transactionally in application code: it saves the `Transaction`, then writes one auto-generated `StockMovement(type: .stockOut, transactionID: transaction.id)` per line — `.stockOut` is never created by hand from the UI (`StockMovementType.manualCases` excludes it; only `.stockIn`/`.correction`/`.opname` are user-selectable, from the item detail screen's overflow menu). `TransactionLine` snapshots `itemCode`/`itemName`/`variantName`/`unitPrice` at sale time, so a later edit or delete of the item never rewrites a historical receipt.

For `.opname` (physical count), the ViewModel converts the entered *counted* quantity into a signed delta (`counted - currentStock`) before saving — the stored `StockMovement.quantity` is always a delta, never an absolute count.

### Localization

English and Bahasa Indonesia, English default. Deliberately **not** Apple's `.strings`/String Catalog — every UI string is decoded from `Resources/Localization/en.json` / `id.json` into the `LocalizedStrings` Codable struct tree (`Localization/LocalizedStrings.swift`), so string keys are compile-time-checked Swift properties (`localization.strings.items.emptyTitle`) rather than free-floating string literals. Adding a new UI string means adding the field to the matching struct **and** both JSON files — the app will `fatalError` at launch if a JSON file doesn't decode, by design (a missing/misspelled key should fail loudly in development, not silently fall back to English).

`Localization/LocalizationManager.swift` is a `@MainActor` `ObservableObject` singleton (`LocalizationManager.shared`) that loads the right JSON, persists the choice in `UserDefaults`, and publishes both `language` and `strings`. It's used two ways:
- **Views** hold it as `@EnvironmentObject` (injected once in `PointApp`) so switching languages in `Views/Settings/SettingsView.swift` re-renders every screen live.
- **ViewModels** read `LocalizationManager.shared.strings` directly for validation-error text (e.g. `ItemFormViewModel.save()`) — they're `@MainActor` too, so this is safe, and it avoids threading an environment object through every ViewModel initializer for what's genuinely global app state.

`StockMovementType` (the model enum) intentionally has **no** `displayName` — its display name is UI content, so it's resolved via `LocalizationManager.displayName(for:)`, not hardcoded on the model.

Each `AppLanguage` case's `nativeName` ("English" / "Bahasa Indonesia") is hardcoded on the enum rather than pulled from the JSON — a language naming itself isn't really "translated" content, matching how iOS's own language picker always shows each language in its own script regardless of the current UI language.

Currency formatting (`Decimal.currencyFormatted`) and system date/time formatting still follow the device's actual locale, not the in-app language toggle — intentionally out of scope; this is a UI-text switch, not a full locale override.

### Printing

`Printing/` holds two deliberately separate classes so "which printer" and "print this one job" can each be reused independently as more print actions get added later:

- **`PrinterManager`** (setup/binding) — `@MainActor` `ObservableObject` singleton (`PrinterManager.shared`), same pattern as `LocalizationManager`. Wraps `UIPrinterPickerController` (AirPrint discovery). `UIPrinter` is a bare `NSObject` in this SDK — no `Codable`, no `NSCoding`/`NSSecureCoding` — so it can't be archived directly; instead `PrinterManager` persists the printer's `url` (`String`) and `displayName` (`String`) as plain `UserDefaults` values and reconstructs the `UIPrinter` via `UIPrinter(url:)` on next launch. `Views/Settings/SettingsView.swift` is the only current UI for binding/clearing a printer.
- **`ReceiptPrinter`** (print action) — builds the plain-text receipt body and hands it to `UIPrintInteractionController`. Checks `PrinterManager.shared.boundPrinter` first: if set, prints straight to it via `controller.print(to:completionHandler:)` with **no picker shown**; otherwise falls back to `controller.present(...)`, which shows the system print sheet (letting the user pick a printer ad hoc, same UX as before a printer was ever bound in Settings). Any future "print" call site (e.g. a reprint action on `TransactionDetailView`) should go through `ReceiptPrinter`, not reimplement `UIPrintInteractionController` setup — that's the reuse boundary this split exists for.

The sale-confirmation flow (`Views/Sales/SaleConfirmationView.swift`) always calls `TransactionFormViewModel.save(_:)` before printing regardless of whether a printer is bound — printing never happens for an unsaved transaction, so a cancelled/failed print can never leave a receipt handed out for a sale that isn't actually on record.
